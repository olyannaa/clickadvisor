Both systems used their recommended real\-time stack and low\-latency ingestion path. CostBench streamed 113\.2 billion stock\-market quotes at a target of **1 million rows per second**, using **matching sorting or clustering keys** and daily **pre\-aggregations** by stock symbol. **Throughout ingestion**, **four interactive aggregate queries** ran every ten minutes; **two drill\-down queries** over raw quotes ran every hour. Every query covered the history ingested so far, including newly arrived quotes. **Read\-side compute was matched at approximately 16 CPUs**, with query\-result caching disabled.

CostBench calculates its **end\-to\-end performance\-per\-dollar score** using the formula shown in the diagram below: **Score \= (① preparation cost \+ ② normalized query cost) × ③ accumulated query runtime.**

Preparation cost covers the complete fresh\-data path. Normalized query cost prices measured query runtimes at the applicable read\-side compute rates. Accumulated query runtime is the sum of query durations. **Lower scores are better.**

**SHARED HARNESS**

 Both systems used the same source files, schema, row decoder, workload generator, AWS EC2 m6i.8xlarge client host, rate controller, scheduler, timing, and result recorder. Only the destination\-specific delivery adapter changed.
 [Part 1 describes the shared methodology.](https://clickhouse.com/blog/costbench-real-time-performance-per-dollar#how-costbench-keeps-the-comparison-fair)

**DATASET AND PREPARATION**

 The complete [NBBO dataset](https://github.com/ClickHouse/CostBench/tree/main/full-path-realtime/quotes#dataset) contains 113\.2 billion narrow, 12\-column rows. Raw tables used `(sym, t)`, stock symbol and event timestamp; daily summaries used `(sym, day)`, stock symbol and day. The summaries maintained the counts, sums, and price minima and maxima used by the aggregate queries.
 

**CONTINUOUS WORKLOAD**

 The client paced fresh rows toward 1 million rows per second while four interactive aggregate queries ran every ten minutes and two drill\-downs every hour. Every query covered the history ingested so far, including the newest quotes. This simulates fresh data being generated continuously and becoming query\-ready as it arrives. It measures the cost and performance of sustaining that workload, rather than the speed of bulk\-loading or backfilling an existing dataset.
