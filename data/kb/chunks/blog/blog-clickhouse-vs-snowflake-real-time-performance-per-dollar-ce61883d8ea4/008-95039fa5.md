Ordinary INSERT requests with [`async_insert`](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse) enabled are buffered on each receiving node. An [adaptive flush timeout](https://clickhouse.com/blog/clickhouse-release-24-02#adaptive-asynchronous-inserts) responds to incoming traffic. Ordering, pre\-aggregation, and [insert\-path transformations](https://github.com/ClickHouse/CostBench/tree/main/docs/clickhouse-native-ingestion) run on those nodes; a dedicated ClickHouse Cloud ingest service can [scale independently](https://clickhouse.com/docs/products/cloud/features/infrastructure/warehouses) from reads while sharing the same stored data.

**SHARED PACING**

Both destinations used the same Parquet source, row decoder, client compute, rate controller, and eight\-worker parallelism. Destination\-specific batching adapted delivery to each API.

**CLICKHOUSE BATCHES**

The client sent [3,000\-row batches](https://github.com/ClickHouse/CostBench/blob/254400222ce969083b67c61e51cab05a2d707df1/full-path-realtime/quotes/clickhouse-cloud/_commands.txt#L60) through asynchronous inserts. With the run’s [default buffering settings](https://clickhouse.com/blog/asynchronous-data-inserts-in-clickhouse), a node flushed at the first of three thresholds: 100 MiB buffered, an adaptive timeout between 50 milliseconds and 1 second, or 450 queued insert queries.

**SNOWFLAKE BATCHES**

Each worker called `append_row` through its own channel. Earlier [stream\-preview evidence](https://github.com/ClickHouse/CostBench/blob/main/full-path-realtime/quotes/snowflake/results/t2/stream_preview.log) for this setup shows the SDK choosing [file mode](https://www.snowflake.com/en/blog/engineering/next-gen-snowpipe-streaming-architecture/) and grouping calls into NDJSON batches averaging approximately 61,500 rows. Across eight channels, that produced about 14\.6 file uploads per second before further server\-side buffering.

**BATCH\-SIZE BOUNDARY**

The 3,000\-row and approximately 61,500\-row figures describe client delivery batches. Both systems buffered them again server\-side, so these figures do not specify final storage\-write sizes.

**RETRIES AND RECOVERY**

Snowpipe Streaming’s [offset tokens](https://docs.snowflake.com/en/user-guide/snowpipe-streaming/snowpipe-streaming-channels) record committed channel progress. A custom application retrieves the last token, maps it to its source, and resumes from the next record; Snowflake’s Kafka connector handles that mapping for Kafka partitions. ClickHouse supports [insert deduplication](https://clickhouse.com/docs/concepts/features/operations/insert/deduplicating-inserts-on-retries) for retries, including [dependent materialized views](https://clickhouse.com/blog/clickhouse-release-26-01#deduplication-of-asynchronous-inserts-with-materialized-views).

**WHERE [CLICKPIPES](https://clickhouse.com/docs/integrations/clickpipes/home) FITS**

Direct application writes are compared here. For Kafka, the corresponding integrations are Snowflake’s Kafka connector and Kafka ClickPipes; for object\-storage files, [classic Snowpipe](https://docs.snowflake.com/en/user-guide/snowpipe-streaming/data-load-snowpipe-streaming-overview#snowpipe-streaming-versus-snowpipe) and Object Storage ClickPipes. Those paths include an external\-source integration beyond the direct\-write boundary measured here.

**STORAGE CONTEXT**

In the [earlier configuration](https://clickhouse.com/blog/real-time-analytics-cost-performance-snowflake-vs-clickhouse), at roughly 113 billion rows, Snowflake’s raw Interactive Table occupied 2\.9 TiB, versus 701 GiB for its standard table and 362 GiB for ClickHouse’s raw table, roughly four and eight times as much. These are earlier\-study footprints, and database storage costs are excluded from this score.
