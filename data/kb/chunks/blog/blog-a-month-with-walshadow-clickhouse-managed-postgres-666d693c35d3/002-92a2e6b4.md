The "Sync to ClickHouse" page in Managed Postgres offers two replication methods: ClickPipes, the existing option, and the newly added WalShadow.

![Figure 1: Choosing between ClickPipes and WalShadow in the first step of the "Sync to ClickHouse" wizard](/_next/image?url=%2Fuploads%2F01_select_replication_engine_1_b1949de1a5.jpg&w=2048&q=75)
*Figure 1: Choosing between ClickPipes and WalShadow in the first step of the "Sync to ClickHouse" wizard*

ClickPipes is a fully managed data pipeline that receives changes through Postgres logical replication. The source does not have to be Managed Postgres; Postgres on Amazon RDS, Google Cloud SQL and others also work[1](#reference-1).

WalShadow does not use logical replication. It receives the same physical WAL that a replica would, decodes it outside Postgres, and writes the result directly to ClickHouse as blocks[2](#reference-2). This approach is possible because ClickHouse manages both sides of the stack, the Postgres source and the ClickHouse destination, which allows a native path from the WAL to ClickHouse. Most managed Postgres services do not expose physical WAL to customers[2](#reference-2). The WalShadow documentation recommends choosing it when you need the lowest latency and the least replication overhead[3](#reference-3).

Over a month of testing, I checked how much the two methods differ with the same source and the same destination, whether the aggregates in the destination stay correct when the application writes only to Postgres, and whether operational events require any action from the user.
