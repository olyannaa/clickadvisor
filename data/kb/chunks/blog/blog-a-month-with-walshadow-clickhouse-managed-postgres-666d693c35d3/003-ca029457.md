I used 16 vCPU for the comparison, a size the WalShadow development team also recommended, so that the source CPU would not become a bottleneck.

## Measuring ClickPipes and WalShadow latency side by side \#

First, I set up WalShadow and ClickPipes on the same source at the same time, replicating into two databases in the same ClickHouse Cloud service. Because both methods replicate the same writes at the same moment, differences in time of day or source state do not affect the comparison.

![Figure 2: Test setup. One source, two methods, two databases in the same ClickHouse Cloud service](/_next/image?url=%2Fuploads%2F02_replication_benchmark_test_setup_color_coded_1_88c50de5aa.png&w=2048&q=75)
*Figure 2: Test setup. One source, two methods, two databases in the same ClickHouse Cloud service*

ClickPipes has two sync settings: Sync interval, which sets how often it writes to the destination, and Pull batch size, the number of rows it reads at a time (100,000 by default). It starts writing when either threshold is reached[4](#reference-4). WalShadow has a Flush timeout setting, the maximum time it waits before writing to the destination. Partway through these measurements, the development team changed the WalShadow Flush timeout to 200 ms[5](#reference-5). The values in the table are from after the change.
