# Detect, act, keep the evidence: node reliability across three clouds

![nikita vaniasin github](/_next/image?url=%2Fuploads%2Fnikita_vaniasin_github_ef33b15af3.jpg&w=96&q=75)![daniel paneda github](/_next/image?url=%2Fuploads%2Fdaniel_paneda_github_4925155708.jpg&w=96&q=75)![eugene babichev github identicon](/_next/image?url=%2Fuploads%2Feugene_babichev_github_identicon_0d7fe097df.png&w=96&q=75)[Nikita Vaniasin](/authors/nikita-vaniasin), [Daniel Paneda](/authors/daniel-paneda) and [Eugene Babichev](/authors/eugene-babichev)Nov 19, 2026 · 19 minutes readClickHouse Cloud runs on many thousands of Kubernetes nodes across AWS, GCP, and Azure. At that scale, a node with a broken disk, a stuck kernel task, or a half\-working network is a daily event. Most of these failures do not look like a node failure at first. Kubernetes still reports the node as Ready. The cloud provider console shows the instance as running. What you see instead is a ClickHouse replica that cannot write to its cache disk, a pod that stays in ContainerCreating, or a query that times out on one replica and works on the others.

While cloud service providers (CSPs) sometimes try to detect and fix these issues, they are not succeeding at these in 100% of cases. Also, the “fix” behavior differs between cloud providers and is not always the optimal solution for a given issue. We wanted to have more control and consistency across CSPs. Hence, we started a project we called Compute Layer Reliability.
