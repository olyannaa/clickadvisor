\# After upgrading to v25\.8\.2\.29, we encountered an issue: **ClickHouse's new version also started using the wrap mechanism to intercept memory allocation and deallocation functions for more precise memory tracking**. This directly conflicted with chDB's existing wrap approach:

```
1chDB's wrap (introduced in Section 2):
2  free(ptr) → __wrap_free() (chDB implementation)
3            → Check memory source (je_mallctl)
4            → Route to je_free or __real_free
5
6ClickHouse new version's wrap:
7  free(ptr) → __wrap_free() (ClickHouse implementation)
8            → Update MemoryTracker statistics
9            → Call je_free
10
11Conflict:
12  Two __wrap_free implementations cannot coexist!
```
Copy command
**Root cause of conflict**:

The linker's wrap mechanism only allows one wrap implementation per symbol. When both ClickHouse kernel and chDB's binding layer try to define `__wrap_free` and other functions, the linker cannot decide which one to use.

### 3\.2 Adaptation solution: Fusing both wrap mechanisms \#

We needed to fuse ClickHouse's memory tracking requirements with chDB's memory source detection requirements into a single wrap implementation:

**Solution approach**:

1. **Keep chDB's wrap implementation** as the final intercept point
2. **Call ClickHouse's MemoryTracker within chDB's wrap**
3. **Decide whether to check memory source based on scenario**

**Final implementation effect**:

Fused `__wrap_free` implementation:

```
1extern "C" void __wrap_free(void * ptr) // NOLINT
2{
3#if USE_JEMALLOC
4    // chDB logic: Check if it's non-jemalloc memory
5    if (tryFreeNonJemallocMemory(ptr))
6        return;  // Already handled glibc-allocated memory via __real_free
7#endif
8    // ClickHouse logic: Update MemoryTracker statistics
9    size_t actual_size = Memory::untrackMemory(ptr, trace);
10#if USE_JEMALLOC
11    // Use jemalloc to release
12    je_free(ptr);
13#else
14    // If jemalloc not enabled, use system free
15    __real_free(ptr);
16#endif
17}
```

### 3\.3 Operator delete problem in dual\-library architecture \#

While implementing the dual\-library architecture introduced in Section 2 (`_chdb.abi3.so` \+ `libpybind11nonlimitedapi_chdb_xx.so`), we discovered that `operator delete` also encountered the same cross\-boundary memory management problem as `free`.

**Problem scenario**:

```
1libpybind11nonlimitedapi_chdb_3.8.so:
2  - Links to glibc at compile time
3  - Calls malloc → Bound to glibc malloc (compile-time symbol binding)
4  - Calls delete during object destruction
5
6_chdb.abi3.so:
7  - Contains jemalloc and operator delete implementation
8  - libpybind11*.so loads _chdb.abi3.so at runtime
9  - delete call → Resolves to definition in _chdb.abi3.so at runtime
```
