`check_entry_exit_locking()` performs lock acquisition and checking. In Q29's scenario:

- **High\-frequency calls**: Regular expression matching generates massive temporary string objects
- **Check on every delete**: Millions of memory deallocations, each calling `je_mallctl("arenas.lookup", ...)`
- **Severe lock contention**: With multi\-threaded parallel execution, `check_entry_exit_locking` becomes a global bottleneck

**Performance profiling data**:

Using `perf` analysis, 99\.8% of CPU time was spent in:

```
1operator delete
2  └─ tryFreeNonJemallocMemory
3      └─ je_mallctl
4          └─ check_entry_exit_locking  ← Hotspot!
5              └─ pthread_mutex_lock
```

### 4\.3 Optimization solution: Introducing disable\_memory\_check \#

Core idea: **Only check memory source where truly needed**.

In chDB's usage scenarios:

- **Inside ClickHouse engine**: All memory allocated by `jemalloc`, no checking needed
- **Python interaction boundary**: May mix Python memory allocators, checking required

Based on this understanding, we introduced the `disable_memory_check` mechanism:

```
1namespace Memory {
2    thread_local bool disable_memory_check{false};  // Disable checking by default inside engine
3}
4
5// Version with conditional checking
6inline ALWAYS_INLINE bool tryFreeNonJemallocMemoryConditional(void * ptr) {
7    if (unlikely(ptr == nullptr))
8        return true;
9
10    // Fast path: Skip checking directly inside engine
11    if (likely(Memory::disable_memory_check))
12        return false;  // Continue normal jemalloc release process
13    ...
14}
15
16// Updated operator delete
17void operator delete(void * ptr) noexcept
18{
19#if USE_JEMALLOC
20    if (tryFreeNonJemallocMemoryConditional(ptr))  // Use conditional version
21        return;
22#endif
23		...
24}
```
