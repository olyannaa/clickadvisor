## An efficient fresh\-data path lowers its own cost \- and the work left for queries \#

> A system can sustain ingestion while its query readiness falls behind.

Keeping up with incoming data does not guarantee that the system is keeping up with everything needed to query it efficiently.

That gap can affect **answer freshness**: new stock quotes may be ingested promptly, yet a risk query can still return results based on an outdated view of the market.

It can also affect **query efficiency**, even when queries can see the latest data. If ordering or pre\-aggregation falls behind, the query engine may need to scan more data, reconcile newer rows, or repeat grouping and aggregation at query time.

The interactive diagram below shows this second effect while data keeps flowing. Watch the loop or drag the slider to see how the query engine’s scanning and aggregation work shrinks as ordering and pre\-aggregation catch up \- and grows when preparation falls behind.

That extra query work consumes read\-side compute, making queries more expensive and answers slower. An efficient fresh\-data path therefore pays off in three ways: **lower preparation cost, lower query cost, and faster answers**.
