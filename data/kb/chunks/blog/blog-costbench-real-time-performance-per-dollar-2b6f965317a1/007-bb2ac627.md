The interactive diagram below shows this second effect while data keeps flowing. Watch the loop or drag the slider to see how the query engine’s scanning and aggregation work shrinks as ordering and pre\-aggregation catch up \- and grows when preparation falls behind.

That extra query work consumes read\-side compute, making queries more expensive and answers slower. An efficient fresh\-data path therefore pays off in three ways: **lower preparation cost, lower query cost, and faster answers**.

## CostBench measures preparation cost, query cost, and runtime under continuous load \#

CostBench follows the same continuously growing dataset from ingestion through row visibility, event\-level layout maintenance, and pre\-aggregation freshness, while aggregate and drill\-down queries run on a fixed schedule. The query definitions stay fixed, but their answers must continually account for newly arriving data. This makes both sides visible: the direct cost of keeping data query\-ready and the performance and cost of serving queries from the state the system actually achieved.

> The first results show that some systems sustained ingestion while pre\-aggregation lag accumulated or query latency rose \- moving more work onto the read path and driving up query\-serving cost.

### How CostBench keeps the comparison fair \#

This round used **push\-based ingestion** across **ClickHouse Cloud**, **Snowflake**, **Databricks**, **BigQuery**, and **Redshift Serverless**: one shared client sent the stream directly through each system’s recommended low\-latency ingest path.
