**Under sustained load, that work can shape performance per dollar as much as query execution itself: it carries its own direct cost, and the state it produces determines how much work remains for the query engine.**

This round tested ClickHouse Cloud, Snowflake, Databricks, BigQuery, and Redshift Serverless using push\-based ingestion. Fresh quotes kept arriving while aggregate and drill\-down queries ran, so each system had to prepare new data and answer queries at the same time.

We’ll first show what makes data query\-ready, then put the systems under continuous load. The results reveal a gap in both runtime and cost. From there, we’ll explain how CostBench combines those dimensions, and why the path from an incoming row to a current answer matters so much.

## What makes data query\-ready \#

Consider a common analytical question about stock quotes: **How many AAPL quote updates arrived each day?**

The query filters for AAPL, groups its quotes by day, and counts the rows in each group:

```
SELECT day, COUNT(*)
FROM quotes
WHERE sym = 'AAPL'
GROUP BY day;
```
Copy command

This is exactly the kind of query analytical systems are built to run fast.

> **Query\-ready data** is organized and prepared so the query engine reads less data and does less work at query time.

For our **“AAPL a day” query**, three steps help the engine read less data and do less work.

### Store data by column \#

Our query needs `sym` to find AAPL’s quotes and `day` to group them. It does not need any other column.

[Columnar storage](https://en.wikipedia.org/wiki/Data_orientation) lets the engine read only those two columns and skip the rest. In the example below, that means reading **2 columns instead of 7**.
