In our example, pruning leaves **three AAPL quotes** to group by day and count. Pre\-aggregation prepares those counts in advance: it groups quotes by `sym` and `day` and calculates `COUNT(*)` for each group. This turns **nine quotes into four summary rows**, each containing a count for one stock on one day.

Because queries may still filter the summary rows, pre\-aggregated data also benefits from a pruning\-friendly physical layout. Our summary rows are ordered by `sym`. For `WHERE sym = 'AAPL'`, the engine reads only the **two AAPL summary rows** and skips the MSFT and NVDA rows. Those two rows already contain the daily counts \- **two quotes on D1 and one on D2** \- so the engine no longer needs to group and count the individual AAPL quotes on every execution.

For time\-sensitive use cases such as monitoring market activity, these summaries must stay current with the underlying quotes, ideally updating as new quotes become queryable.

For our AAPL query, **columnar storage** lets the engine skip unused fields, **sorting by `sym`** lets it skip unrelated stocks, and **current pre\-aggregations** let it skip grouping and counting individual quotes. Together, these preparations make data **query\-ready for analytical queries like this one**: the query engine reads less data and performs fewer calculations.
