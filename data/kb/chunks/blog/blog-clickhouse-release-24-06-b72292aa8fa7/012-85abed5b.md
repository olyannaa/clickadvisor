might be to order the table by `(mercator_x, mercator_y)` \- ordering data first by `mercator_x` and then `mercator_y.` This actually delivers a significant improvement in query performance time by reducing the number of rows read to 42 million:

```
1CREATE TABLE noaa_lat_lon
2(
3	`station_id` LowCardinality(String),
4	…
5	`mercator_x` UInt32 MATERIALIZED mercator(location).1,
6	`mercator_y` UInt32 MATERIALIZED mercator(location).2
7)
8ENGINE = MergeTree
9ORDER BY (mercator_x, mercator_y)
10
11--populate from existing
12INSERT INTO noaa_lat_lon SELECT * FROM noaa
13
14WITH
15	mercator((5.152588, 44.184654)) AS bottom_left,
16	mercator((16.226807, 47.778548)) AS upper_right
17SELECT
18	toWeek(date) AS week,
19	sum(snowfall) / 10 AS total_snowfall,
20	avg(snowDepth) AS avg_snowDepth
21FROM noaa_lat_lon
22WHERE (mercator_x >= (bottom_left.1)) AND (mercator_x < (upper_right.1)) AND (mercator_y >= (upper_right.2)) AND (mercator_y < (bottom_left.2))
23GROUP BY week
24ORDER BY week ASC
25
26--results omitted for brevity
2754 rows in set. Elapsed: 0.197 sec. Processed 42.37 million rows, 213.44 MB (214.70 million rows/s., 1.08 GB/s.)
```

> As a side note, experienced ClickHouse users might be tempted to use the function `pointInPolygon` here. This does not unfortunately currently exploit the index and [results in slower performance](https://pastila.nl/?00516978/d9292dfc7760b2d3133abd7c237057e9#Bx9BxsWXshOqof1h67EvCw==).

We can see this key is relatively effective at filtering granules, reducing the number to read to 5172, by using the `EXPLAIN indexes=1` clause.

```
1EXPLAIN indexes = 1
2WITH
3	mercator((5.152588, 44.184654)) AS bottom_left,
4	mercator((16.226807, 47.778548)) AS upper_right
5SELECT
6	toWeek(date) AS week,
7	sum(snowfall) / 10 AS total_snowfall,
8	avg(snowDepth) AS avg_snowDepth
9FROM noaa_lat_lon
10WHERE (mercator_x >= (bottom_left.1)) AND (mercator_x < (upper_right.1)) AND (mercator_y >= (upper_right.2)) AND (mercator_y < (bottom_left.2))
11GROUP BY week
12ORDER BY week ASC
```

However, the above 2\-level sorting does not guarantee points that are in close proximity reside in the same granules. A Hilbert encoding should provide this property, allowing us to filter granules even more effectively. For this, we need to modify the table `ORDER BY` to `hilbertEncode(mercator_x, mercator_y).`
