We are not reusing failed primaries. Nothing in the control plane attaches the user NIC again, and it stays detached until the old VM is destroyed, so it is OK to use the force option in our case.

Here is an example where this fencing mechanism works in real life. Below are control plane logs of a failover on AWS:

```
121:19:40 respirate.2 | {"ssh":{...,"cmd":"timeout 10 sudo pg_ctlcluster 18 main stop -m immediate","exit_code":2,...,"stdout":"Cluster is not running.\n",...}
221:19:40 respirate.1 | {"ssh":{...,"cmd":"timeout 10 sudo postgres/bin/lockout-hba 18","exit_code":1,...,"stderr":"... command failed: sudo pg_ctlcluster 18 main reload (CommandFail)...
321:19:42 respirate.1 | {"fenced_unresponsive_primary":{...,"mechanism":"detach_nic"},"message":"Fenced unresponsive primary",...}
421:19:42 respirate.2 | {"strand_hopped":{...,"from":"Postgres::PostgresServerNexus.wait_representative_lockout","to":"Postgres::PostgresServerNexus.prepare_taking_over"},...}
```

The `pg_stop` mechanism found no running cluster, and `hba` could not reload, which is expected after a SIGKILL. So the detach was the only mechanism that succeeded, and the standby moved on to the promotion. Thirteen seconds later, the control plane saved the kernel log of the old primary over the management NIC, and this was its last line:

```
12026-08-26T21:19:42,694874+00:00 pcieport 0000:26:00.1: pciehp: Slot(36): Button press: will power off in 5 sec
```
