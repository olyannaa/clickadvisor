CostBench calculates its **end\-to\-end performance\-per\-dollar score** using the formula shown below: **Score \= (① preparation cost \+ ② normalized query cost) × ③ accumulated query runtime.**

Preparation cost covers the complete fresh\-data path. Normalized query cost prices recorded query runtimes at the applicable read\-side compute rates. Accumulated query runtime is the sum of query durations. **Lower scores are better.**

**SHARED HARNESS**

Both systems used the same source dataset, schema, workload definitions, pacing model, query schedule, and result format. Destination\-specific adapters handled delivery and timing. [Part 1](https://clickhouse.com/blog/costbench-real-time-performance-per-dollar) explains the shared methodology; the [Databricks benchmark contract](https://github.com/ClickHouse/CostBench/blob/main/full-path-realtime/quotes/databricks/DATABRICKS_BENCHMARK_CONTRACT.md) records this provider’s implementation.

**DATASET AND PREPARATION**

The complete [NBBO dataset](https://github.com/ClickHouse/CostBench/blob/main/full-path-realtime/quotes#dataset) contains 113,219,565,734 narrow, 12\-column rows. Raw tables used (sym, t), stock symbol and event timestamp; daily summaries used (sym, day), stock symbol and UTC day. The summaries maintained the counts, sums, and price minima and maxima used by the aggregate queries.

**CONTINUOUS WORKLOAD**

Fresh rows were paced toward 1 million per second while aggregate and drill\-down queries ran on their ten\-minute and hourly schedules. This models data being generated continuously and prepared as it arrives, rather than measuring how quickly an existing dataset can be bulk\-loaded or backfilled. The Databricks MV path retained its native snapshot semantics; matching ingestion progress does not make both systems’ summaries equally fresh.

**RECOMMENDED STACK AND SIZING**

ClickHouse Cloud used a 16\-CPU, 64\-GiB read node. Databricks used an X\-Small Serverless SQL warehouse fixed at one cluster, approximately 16 worker vCPUs; this sizing does not imply identical hardware or memory. [Liquid clustering](https://docs.databricks.com/aws/en/tables/clustering), [Predictive Optimization](https://docs.databricks.com/aws/en/optimizations/predictive-optimization), and triggered incremental MV refresh were enabled. Lakehouse//RT was unavailable in the test workspace, so the accepted comparison uses the [Serverless SQL baseline](https://github.com/ClickHouse/CostBench/blob/main/full-path-realtime/quotes/databricks/REAL_SERVERLESS_BASELINE.md).

**① PREPARATION COST**

The full ingest includes ClickHouse’s complete two\-node HA ingest service and Databricks’ Zerobus ingestion, asynchronous clustering, and MV refresh. Databricks ingestion and refresh use allocated DBU usage; clustering uses the accepted Predictive Optimization DBU allocation. All three appear in the [preparation\-cost model](https://github.com/ClickHouse/CostBench/blob/main/full-path-realtime/quotes/databricks/costs/out/serverless_20260918/fresh_data_path.json).
