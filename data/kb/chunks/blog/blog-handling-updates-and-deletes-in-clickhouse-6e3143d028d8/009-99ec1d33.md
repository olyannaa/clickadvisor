Rows to update are identified based on the sorting key used in the `ORDER BY ()` DDL statement when creating the table: ![collapsing_merge_tree.png](/_next/image?url=%2Fuploads%2Fcollapsing_merge_tree_ceb2d258bb.png&w=2048&q=75)

To satisfy the deduplication condition on the sorting key, we have to insert the same value for the `read_start, article_id, user_id` columns to update a row. For example, when a user starts reading an article, we insert the following row:

```
1INSERT INTO article_reads
2            VALUES(1, 12, 0, now(), now(), 1);
```
Copy command
We now have a single row in the table:

```
1SELECT *
2FROM article_reads
3
4┌─user_id─┬─article_id─┬─read_to─┬──────────read_start─┬────────────read_end─┬─sign─┐
5│       1 │         12 │       0 │ 2023-01-06 15:20:32 │ 2023-01-06 15:20:32 │    1 │
6└─────────┴────────────┴─────────┴─────────────────────┴─────────────────────┴──────┘
```
Copy command
A minute later, when the user reaches 70% of our article, we insert the following 2 rows:

```
1INSERT INTO article_reads
2            VALUES(1, 12, 0, '2023-01-06 15:20:32', now(), -1),
3                  (1, 12, 70, '2023-01-06 15:20:32', now(), 1);
```
Copy command
The first row with `sign=-1` is used to tell ClickHouse it should delete the existing row (based on values in the ORDER BY tuple \- `read_start`, `article_id` and `user_id` columns). The second inserted row (with `sign=1`) is the new row with the `read_to` column set to the new value of `70`.

Since data updates are [happening in the background](https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/collapsingmergetree/#table_engine-collapsingmergetree-collapsing-algorithm), with eventual consistency of results, we should filter on the `sign` column to get correct results:

```
1SELECT
2    article_id,
3    user_id,
4    max(read_end),
5    max(read_to)
6FROM article_reads
7WHERE sign = 1
8GROUP BY
9    user_id,
10    article_id
11
12┌─article_id─┬─user_id─┬───────max(read_end)─┬─max(read_to)─┐
13│         12 │       1 │ 2023-01-06 15:21:59 │           70 │
14└────────────┴─────────┴─────────────────────┴──────────────┘
15
161 row in set. Elapsed: 0.004 sec.
```
Copy command
The `CollapsingMergreTree` engine will now take care of removing canceled rows from storage efficiently in the background, so we don’t have to delete them manually. You can find further examples of using the CollapsingMergeTree engine [here](https://www.google.com/url?q=https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/collapsingmergetree/%23example-of-use&sa=D&source=docs&ust=1678440218544759&usg=AOvVaw3vOSZ1Rbl24kvzHT48kuyp).
