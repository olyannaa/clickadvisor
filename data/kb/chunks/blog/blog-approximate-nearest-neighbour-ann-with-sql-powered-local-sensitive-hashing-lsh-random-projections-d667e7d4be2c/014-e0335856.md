```
1WITH
2   'dog' AS search_term,
3   (
4       SELECT vector
5       FROM glove
6       WHERE word = search_term
7       LIMIT 1
8   ) AS target_vector,
9   128 AS num_bits,
10   (
11       SELECT
12           groupArray(normal) AS normals,
13           groupArray(offset) AS offsets
14       FROM
15       (
16           SELECT *
17           FROM planes
18           LIMIT num_bits
19       )
20   ) AS partition,
21   partition.1 AS normals,
22   partition.2 AS offsets,
23   (
24       SELECT arraySum((normal, offset, bit) -> bitShiftLeft(toUInt128(dotProduct(target_vector - offset, normal) > 0), bit), normals, offsets, range(num_bits))
25   ) AS target
26SELECT
27   word,
28   bitHammingDistance(bits, target) AS approx_distance,
29   cosineDistance(vector, target_vector) AS score
30FROM glove_lsh
31PREWHERE approx_distance <= 5
32WHERE word != search_term
33ORDER BY score ASC
34LIMIT 5
```

So we’ve achieved a 10x speedup in performance and retained quality!
An astute reader will have noticed the filter by the value of 5 \- effectively, the number of bits that are different. This is within a maximum range of 128\. How did we select this value?

Trial and error. This value should be robust across different search terms but will depend on the distribution of vectors in your space. A value that is too high and insufficient rows will be filtered prior to distance scoring, providing minimal performance benefit. Too low a value, and the desired results will be filtered out.
