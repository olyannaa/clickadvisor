The ordering of raw and summary data established during preparation lets ClickHouse’s [sparse primary index](https://clickhouse.com/blog/index-based-pruning) skip irrelevant ranges. [Projections](https://clickhouse.com/blog/projections-secondary-indices) extend this approach with alternative data orderings and their own indexes.

[Skipping continues during execution](https://clickhouse.com/blog/streaming-secondary-indices). [PREWHERE](https://clickhouse.com/docs/concepts/features/performance/prewhere) applies filters before additional columns are loaded. Optimizations for [common query patterns such as Top\-N](https://clickhouse.com/blog/clickhouse-top-n-queries-granule-level-data-skipping) further reduce the work required by `ORDER BY … LIMIT`, skipping data that cannot improve the result. [Lazy materialization](https://clickhouse.com/blog/clickhouse-gets-lazier-and-faster-introducing-lazy-materialization) can defer reading output columns until the result rows are known.

ClickHouse also uses [caches at several levels](https://clickhouse.com/docs/concepts/features/performance/caches/caches) to avoid repeatedly fetching metadata and data, decompressing and decoding columns, or evaluating the same filters.

These are only some of ClickHouse’s query optimizations. [Statistics](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/mergetree#column-statistics) guide query planning, and query rewrites eliminate redundant calculations before execution. Other techniques include just\-in\-time compilation of frequently used expressions and using existing data order to satisfy `ORDER BY` without an additional sort or to simplify aggregation. Our [VLDB research paper](https://www.vldb.org/pvldb/vol17/p3731-schulze.pdf) describes these techniques and the wider engine architecture in more detail.

### The engine’s performance in numbers \#

We also monitored the read service (via the [built\-in ClickHouse Cloud advanced dashboard](https://clickhouse.com/docs/products/cloud/features/monitoring/advanced-dashboard)) during query execution, tracking processing throughput alongside CPU and memory use.

**As shown earlier, ClickHouse Cloud accumulated the least query runtime and the lowest query cost across all four comparisons.** Query compute was aligned where possible; where it differed, the score showed whether any extra query speed justified the extra compute cost.

ClickHouse achieved these results using a separate, single\-node read service with **16 CPU cores and 64 GiB of memory**, while fresh quotes continued to be ingested and prepared. At **113\.2 billion quotes**, the four interactive aggregate queries returned responses averaging about **15 ms**, while the two raw\-data drill\-downs averaged **roughly one second**.

The two full\-history aggregates, A3 and A4, answered from prepared summaries at an **effective aggregation throughput of about six trillion quotes per second**. That rate measures the raw quote history represented by their summaries per second of query execution.
