CostBench setup, [On\-Demand Compute](https://clickhouse.com/blog/on-demand-compute) lets eligible queries request **temporary stateless workers** through the existing service. These workers provide additional query capacity without permanently increasing the service’s size. The shared\-data architecture also supports several ways to distribute query work:

- [Parallel replicas](https://clickhouse.com/blog/clickhouse-parallel-replicas) distribute reads and aggregation across nodes.
- [Index sharding](https://clickhouse.com/blog/index-sharding-clickhouse-cloud-petabyte-scale-indexing) distributes index analysis across nodes.
- [Multi\-stage execution](https://clickhouse.com/blog/multi-stage-distributed-query-execution-clickhouse-cloud) dynamically spreads large joins and high\-cardinality aggregations across nodes.

Ingest nodes, read nodes, and temporary stateless query workers all run the same [ClickHouse engine](https://www.vldb.org/pvldb/vol17/p3731-schulze.pdf).

One engine integrates the full analytical path (click to expand)

Data preparation (including [insert\-time transformations](https://github.com/ClickHouse/CostBench/blob/main/docs/clickhouse-native-ingestion/README.md)), parallelized query processing, and the distributed execution mechanisms described above are built into it.

ClickHouse Cloud can scale compute independently by workload while retaining common SQL functions, data types, and execution machinery. For developers, this provides a consistent set of building blocks for understanding and debugging the full analytical path. Improvements to shared engine code can benefit every role that uses it.

How does one parallelized query scale across nodes? (click to expand)

The chart below shows a [separate experiment](https://clickhouse.com/blog/clickhouse-parallel-replicas#scaling-at-1t-rows) over a fully loaded UK property\-price dataset. One query groups **1 trillion raw rows** by county, town, and district, calculating counts, sums, and averages. It uses 1 to 100 nodes with 89 CPU cores each, without pre\-aggregation or redistributing stored data.

Data processing throughput rose from **6\.49 GB/s** on one node to **519\.18 GB/s** on 100 nodes. Each plotted point is the fastest of ten runs at that configuration.

The same article also demonstrates a [simpler aggregation](https://clickhouse.com/blog/clickhouse-parallel-replicas#group-by-at-the-speed-of-clickhouse): summing prices by town over **100 billion raw rows**. It finished in **0\.414 seconds**, processing **241\.8 billion rows per second**, or **1\.45 TB/s**. The recording below shows the query in action.

These raw\-data experiments demonstrate distributed execution on already\-loaded data. CostBench measures a different workload: continuously preparing fresh quotes and serving queries, including both stages in its performance\-per\-dollar score.
