**② Order data:** The streaming view used SORTKEY (sym, t), with DISTSTYLE EVEN to preserve scan parallelism for symbol filters. Redshift [sorts in the background](https://docs.aws.amazon.com/redshift/latest/dg/t_Reclaiming_storage_space202.html#automatic-table-sort), so newly arrived rows can be visible before that layout work is complete.

**③ Order and pre\-aggregate data:** A separate daily MV groups directly from the streaming view by (sym, day), with its own sort key. A controller repeatedly issues incremental [REFRESH MATERIALIZED VIEW ... RESTRICT](https://docs.aws.amazon.com/redshift/latest/dg/materialized-view-refresh-sql-command.html). The daily MV and a typed raw projection are sibling branches; daily summaries do not wait for the typed branch.

> The result: Redshift’s streaming view, background sorting, and daily summaries advance through separate stages, so queries can encounter unfinished preparation.

Why these ingestion paths, and how were they buffered? (click to expand)

**The same ingestion problem:**

The source produces frequent writes that must become efficient analytical storage. ClickHouse accepts them through native asynchronous inserts. Redshift’s recommended high\-rate streaming path includes an MSK broker cluster plus a consuming writer workgroup; both belong in preparation cost.

**Redshift’s streaming path:**

The [producer](https://github.com/ClickHouse/CostBench/blob/main/full-path-realtime/quotes/redshift-serverless/broker/produce_quotes.py) used **16 processes** and lz4 compression. MSK provided three brokers across three availability zones, with 24 partitions and replication factor three. Redshift consumed the stream directly; no intermediate S3 load job was added.

**ClickHouse’s native path:**

Ordinary INSERT requests with async\_insert enabled were buffered on each receiving node. An [adaptive flush timeout](https://clickhouse.com/docs/optimize/asynchronous-inserts) responded to incoming traffic. Ordering and pre\-aggregation ran on the ingest nodes; the dedicated [ingest service](https://clickhouse.com/docs/cloud/reference/warehouses) shared storage with the independently sized read service.

**Shared pacing:**

Both adapters read the same Parquet dataset and decoded the same schema under the same target\-rate model. Parallelism and client batch sizes were adapted to each destination’s API; they were not forced to be identical.

**ClickHouse batches:**

The client sent 3,000\-row batches through asynchronous inserts. Default buffering flushed at the first of three thresholds: 100 MiB buffered, an adaptive timeout between 50 milliseconds and 1 second, or 450 queued insert queries.

**Redshift delivery:**

Producer acknowledgments report Kafka delivery, not completion of all downstream views. Streaming ingestion advances the raw streaming view; separate refresh transactions advance the typed projection and daily summaries.

**Batch\-size boundary:**

Client INSERT batches and Kafka batches are transport units. They do not define the final MergeTree part, Redshift storage block, or daily\-MV refresh size.
